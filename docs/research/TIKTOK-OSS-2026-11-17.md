# TikTok: повторная проверка open-source коннекторов

Проверено 17 ноября 2026 года по GitHub API, исходникам и документации владельцев проектов. Это исследование: новые библиотеки не устанавливались, вход в TikTok и дополнительные живые сборы не выполнялись. Проверенный ранее в e-content результат — 20 комментариев одного ролика после ручного гостевого подтверждения — описан отдельно в [текущем адаптере](../architecture/tiktok-public.md). Он не является проверкой перечисленных библиотек.

## Вывод для выбора

Готовые бесплатные реализации получения списка роликов, комментариев и публичных счётчиков существуют. Однако библиотека чтения и надёжное пользовательское подключение — разные части. Наличие `msToken`, cookies или файла профиля не доказывает, что TikTok признаёт сессию действующей. «Сохранили состояние» должно дополняться проверкой текущего аккаунта и реальной возможностью прочитать его ролики. Это хорошо видно в [OpenTok session.ts](https://github.com/caixax/opentok/blob/2e0544003945c59016ed7b74c4575bd063774d13/src/main/tiktok/session.ts) и [pytok account verification](https://github.com/MEOMcGill/pytok/blob/b04636c9c137d5b7622516f74af4d6a12a0d035f/pytok/tiktok.py).

**Первый кандидат — TikTokApi 7.3.5, исключительно для небольшого воспроизводимого стенда, не для немедленной интеграции. Запасной — DTK v5 как отдельный сервис.** Выбор SDK обусловлен размером интеграции с нашим локальным Node/SQLite-приложением, а не доказанной большей надёжностью. У TikTokApi найдено сомнительное соответствие `item_id` в запросе ответов; пока не проверены именно тексты комментариев и вложенных ответов, кандидат не допущен к цеху. DTK имеет более развитую инфраструктуру, но значительно тяжелее в сопровождении. Если оба не проходят проверку без обязательной платной инфраструктуры, это результат исследования, а не повод незаметно включать платный fallback.

Для публичных данных сначала проверяем **гостевую сессию и один заданный профиль**, без основного аккаунта. `msToken` не равен авторизации пользователя: наличие токена означает лишь материал для web-запросов. Обязательность cookies основного аккаунта исходниками TikTokApi не установлена. Если понадобится авторизация, её необходимость и возможность чтения проверяются отдельно; сохранение cookies само по себе не подтверждает рабочий аккаунт.

## Что подтверждено исходниками

### davidteather/TikTok-Api

Python + Playwright. `User.videos()` получает страницы `/api/post/item_list/`; `Video.comments()` — `/api/comment/list/`; `Comment.replies()` — отдельные страницы ответов. Таким образом, пользовательские ссылки на каждый ролик технически не обязательны: профиль можно обходить программно. [user.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/api/user.py), [video.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/api/video.py), [comment.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/api/comment.py).

`create_sessions()` принимает cookies, `ms_tokens`, параметры контекста и фабрики браузера/страницы. По умолчанию создаются новые браузерные контексты; отсутствие переданного `msToken` приводит к попытке прочитать его из visitor cookies. Вход и `sessionid` не являются обязательными параметрами. `User.videos()` при отсутствии `sec_uid` сам вызывает `info()`: старт по `@handle` реализован, вручную перечислять ролики не нужно. Возможность получить данные без входа в нашей сети требует отдельной проверки. [user.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/api/user.py), [tiktok.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/tiktok.py).

SDK подписывает URL через JavaScript страницы (`generate_x_bogus`, `sign_url`) и выполняет `fetch` в Playwright. Проверка `_is_session_valid` проверяет живой browser/page, а не текущую личность TikTok. Для постоянного подключения нужны собственные жизненный цикл, проверка аккаунта и сохранение обновлённого состояния; фабрика контекста позволяет организовать выделенный профиль. `make_request()` имеет retries, exponential backoff и повтор с другой сессией; внутренние попытки и разрешённая политика восстановления должны контролироваться нашим worker. [tiktok.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/tiktok.py).

Высокоуровневые генераторы страниц требуют обёртки: внешний `count` не гарантирует строгий остаток нашего бюджета внутри полученной страницы; нужны дедупликация, запрет повторяющегося курсора и отдельный бюджет ответов. **Проверенное наблюдение из кода:** `Comment.replies()` передаёт `item_id=self.author.user_id`, а `author` извлекается из `user` автора комментария. **Интерпретация:** для endpoint ответов ожидается ID ролика; привязка выглядит дефектной и требует проверки/исправления. Live-отказ этим исследованием не доказан. Наличие метода `replies()` не считается подтверждением работоспособности ответов. [comment.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/api/comment.py). Открытый [issue #1311](https://github.com/davidteather/TikTok-Api/issues/1311), обновлённый 2026-11-09, описывает `200` с пустым телом для user-запросов. Ни название issue, ни популярность SDK не устанавливают причину сбоя у нас.

**Windows и стоимость сопровождения:** пакет требует Python >=3.9, Playwright и браузерный runtime. Для стенда разумно фиксировать Python 3.12 и версии зависимостей; Windows-работоспособность конкретного окружения пока не проверена. Развёртывание существенно меньше DTK, но подпись и web-endpoints остаются изменяемыми, поэтому сопровождение оценивается как среднее. Упомянутые в README TikAPI/EnsembleData — партнёры, не обязательный платёж; proxy-поддержка тоже не доказывает обязательность покупки proxy. [setup.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/setup.py), [README](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/README.md).

### Evil0ctal/DTK v5

Репозиторий по-прежнему расположен по адресу `Evil0ctal/Douyin_TikTok_Download_API`, но текущий код — DTK v5: REST/MCP, консоль и worker. Имеются отдельные endpoints роликов автора, корневых комментариев, ответов и информации о текущем аккаунте. [endpoints.py](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/platforms/tiktok/endpoints.py), [adapter.py](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/platforms/tiktok/adapter.py).

В текущем DTK есть **нативная pure-Python подпись TikTok `X-Dynosaur` / `X-Gnarly`** и HTTP transport `wreq`. Это существенное отличие от старого описания проекта: browser RPC не обязателен для каждого запроса. `requires_browser_signature()` для TikTok зависит от наличия `msToken`: импортированный cookie jar с токеном может идти нативным путём. Браузер остаётся способом получения новых гостевых identities для TikTok и вариантом fallback. Это подтверждение архитектуры кода, не наш live-тест подписей. [tiktok_sign.py](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/signing/native/tiktok_sign.py), [signer.py](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/signing/native/signer.py), [protection.py](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/signing/protection.py), [native minting](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/identity/minting/native.py).

FAQ явно допускает запуск без browser profile с ручным импортом jar, в том числе **гостевых cookies без входа**, и прямое соединение, если proxy не заданы. Платные solver/proxy/SaaS не являются обязательным условием этой конфигурации. Это не обещает доступность из нашей сети и не делает анонимные cookies бессрочными. Согласованность параметров подписи, браузерного отпечатка и transport важна; нельзя обещать, что простое копирование cookies из Zen в любой HTTP-клиент заработает. [FAQ](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/documents/en/17-faq.md), [native signer](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/signing/native/signer.py).

**Но это сервис, не выделенный компактный SDK:** Python >=3.12,<3.14, PostgreSQL/TimescaleDB, Redis, миграции и отдельные API/worker. В проверенных документах публичный контракт — REST/MCP; `dtk.__init__` экспортирует версию, а Python entrypoint — CLI. Документированного стабильного standalone-клиента, который можно импортировать только для трёх TikTok endpoints, не найдено. Выдёргивание внутренних signing/identity/transport модулей создаст наш собственный сопровождаемый форк. Ключ DTK относится к собственному серверу и не является официальным разрешением TikTok. [pyproject.toml](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/pyproject.toml), [package init](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/__init__.py), [Installation](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/documents/en/02-installation.md), [API](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/documents/en/11-api.md).

**Windows:** документация установки ориентируется на Linux/macOS/WSL2; для нашего Windows логичный стенд — Docker/WSL2. Нативный signer написан на Python, а `wreq 0.13.0` имеет готовые Windows wheels для x86/x64/ARM64 и требует Python >=3.11. Значит, запрет Windows со стороны `wreq` не установлен; но это не доказывает поддержку всей DTK-инфраструктуры в обычном PowerShell. [wreq package files](https://pypi.org/project/wreq/0.13.0/#files), [Installation](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/documents/en/02-installation.md).

**Оценка:** второй кандидат для изолированного сравнения, если компактный SDK непригоден. Миграция всего e-content на DTK сейчас несоразмерна задаче. Не переносить автоматически account rotation, minting identities и их retry-политику в наш продукт.

### JoeanAmier/TikTokDownloader

TikTok endpoints комментариев, ответов и списка роликов действительно есть. Это не исключительно Douyin. [comment_tiktok.py](https://github.com/JoeanAmier/TikTokDownloader/blob/f766a6eff25b76fe4d737f10c27258e4da65df7d/src/interface/comment_tiktok.py), [account_tiktok.py](https://github.com/JoeanAmier/TikTokDownloader/blob/f766a6eff25b76fe4d737f10c27258e4da65df7d/src/interface/account_tiktok.py).

Но текущий cookie UX — ручная передача/clipboard и сохранение в конфигурации, не готовое «вошёл в e-content и забыл». Release 5.8 явно удалил чтение cookies браузера и вернул ручной ввод; отдельные обещания английского README устарели. [cookie.py](https://github.com/JoeanAmier/TikTokDownloader/blob/f766a6eff25b76fe4d737f10c27258e4da65df7d/src/module/cookie.py), [release 5.8](https://github.com/JoeanAmier/TikTokDownloader/releases/tag/5.8).

Стек включает downloader, FastAPI, `curl_cffi` и собственную реализацию изменяющихся web-параметров. Параметр `needPinnedItemIds=true` в profile listing не является сортировкой последних N по дате. **Оценка:** полезный сравнительный источник, но пользовательскую проблему постоянного подключения сам по себе не решает; большой стек и GPL требуют отдельного решения перед включением.

### MEOMcGill/pytok

Функционально особенно близок задаче: постоянный `user_data_dir`, ручной вход, привязка ожидаемого аккаунта и проверка фактически вошедшей личности. Discovery различает пустой/обрезанный список и действительное завершение, объединяет первоначальные данные, API и DOM с дедупликацией. [tiktok.py](https://github.com/MEOMcGill/pytok/blob/b04636c9c137d5b7622516f74af4d6a12a0d035f/pytok/tiktok.py), [user.py](https://github.com/MEOMcGill/pytok/blob/b04636c9c137d5b7622516f74af4d6a12a0d035f/pytok/api/user.py).

Есть отдельные методы комментариев и ответов. Однако count корневых комментариев не следует принимать за общий предел с вложенными репликами: ответы подгружаются отдельно. [video.py](https://github.com/MEOMcGill/pytok/blob/b04636c9c137d5b7622516f74af4d6a12a0d035f/pytok/api/video.py).

Главное препятствие — [PolyForm Noncommercial](https://github.com/MEOMcGill/pytok/blob/b04636c9c137d5b7622516f74af4d6a12a0d035f/LICENSE): это нельзя представлять как MIT-подобную свободную зависимость для любого развиваемого продукта. Camoufox и локальный автоматический CAPTCHA solver присутствуют в текущем проекте, но есть параметр `manual_captcha_solves`; **обязательный платный solver не установлен**. Это дополнительная браузерная сложность, а не доказательство обязательной оплаты. [pyproject.toml](https://github.com/MEOMcGill/pytok/blob/b04636c9c137d5b7622516f74af4d6a12a0d035f/pyproject.toml), [constructor](https://github.com/MEOMcGill/pytok/blob/b04636c9c137d5b7622516f74af4d6a12a0d035f/pytok/tiktok.py). Автоматические CAPTCHA и смена аккаунтов не нужны для предложенного подключения и не должны включаться за пользователя. Открытый [issue #66](https://github.com/MEOMcGill/pytok/issues/66) от 2026-10-28 описывает search cap; он не устанавливает причину нашего сбоя.

**Оценка:** хороший архитектурный референс, не безусловная бесплатная зависимость для развиваемого продукта.

### caixax/opentok

Electron/TypeScript-клиент с постоянной partition `persist:tiktok` и ручным входом на реальном сайте, включая QR. Пригоден как пример сохранения одной личности между запусками. Особая ценность — проверка account info: код не принимает наличие `sessionid` за доказательство действующей сессии. Но внутренний health endpoint и его успешную структуру надо заново проверить у нас; документация проекта сама отмечает непроверенные части. [session.ts](https://github.com/caixax/opentok/blob/2e0544003945c59016ed7b74c4575bd063774d13/src/main/tiktok/session.ts), [TIKTOK-API.md](https://github.com/caixax/opentok/blob/2e0544003945c59016ed7b74c4575bd063774d13/docs/TIKTOK-API.md).

В описании есть profile pagination и комментарии, но новый запрос не становится надёжным из-за авторизации. Документ неоднозначно трактует пустое тело то как CAPTCHA, то как throttling. У нас причина должна оставаться неопределённой до дополнительной проверки, а не подменяться предположением. [Тот же документ](https://github.com/caixax/opentok/blob/2e0544003945c59016ed7b74c4575bd063774d13/docs/TIKTOK-API.md).

**Оценка:** MIT-референс session manager; архивирован 15 октября 2026 года, поэтому не основная поддерживаемая зависимость. Ради этих приёмов не требуется превращать весь текущий сайт в Electron.

## Что должны гарантировать наши модули поверх любой библиотеки

1. Подключение и цели анализа разделены: гостевой collector читает публичный профиль по handle; авторизованное подключение добавляется только при подтверждённой необходимости. Для него — один отдельно выделенный профиль и ручной вход на TikTok, проверка фактической личности и чтения. Не использовать одновременно открытый профиль обычного браузера как рабочую базу worker.
2. Профиль для анализа задаётся один раз. При авторизации собственный профиль определяется из проверенного аккаунта; другие выбранные профили остаются отдельными целями. URL каждого ролика не нужен.
3. «Последние 10/20» — наш явный алгоритм по `createTime`, а не первые 10/20 карточек. Закреплённые старые ролики не должны вытеснять свежие. При недостаточной выборке или неподтверждённом порядке выдачи показывать ограничение полноты, а не выдавать результат за точные последние N.
4. Ролики, комментарии и ответы обходятся отдельными курсорами с дедупликацией и строгим общим пределом. Не доверять названиям `count`/`batch_size` как общей квоте.
5. Учёт реальных запросов, пагинации, SDK retries и browser assets. Пустой `200`, `has_more` без новых ID, повтор курсора, 401/403/429 — разные диагностируемые события. Автологин или автоматическая смена аккаунта не являются восстановлением по умолчанию.
6. Сохранять нормализованные ролики/комментарии и снимки публичных счётчиков в SQLite. Данные: текст/описание, ID, дата, parent/root, лайки, просмотры/репосты/комментарии при наличии. Удержание, источники просмотров и исторические ряды нельзя выводить из этих полей.
7. Браузерные cookies не обладают гарантированным бессрочным сроком. Повторный вход нужен по фактической инвалидизации сессии, а не после закрытия UI. Результаты и курсоры остаются при отмене/ошибке, повторный запрос не создаёт дубликаты идей.

Это инженерные требования к нашему модулю, а не утверждение, что сторонние репозитории уже реализуют все перечисленные гарантии.

## Малый стенд и критерий допуска

Стенд не меняет существующие данные или исполнение цеха. Фиксируем SHA/версию, конфигурацию и окружение; сохраняем обезличенные сырые ответы и нормализованный результат. Первый прогон — TikTokApi, один public handle, одна guest web-сессия, прямое соединение, без main-account cookies, облачных fallback, ротации аккаунтов и автоматических CAPTCHA. Лимиты опыта — 10/20 роликов и небольшой заранее выбранный объём комментариев, а не API-квота или утверждение о безопасном пороге TikTok.

| Проверка                       | Условие допуска                                                                                                                                                                           |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Профиль → последние N          | Совпадают ID и даты с видимыми свежими роликами; старые закрепления не подменяют новые; неполный ответ обозначен как неполный                                                             |
| Основная функция               | Получены **тексты** корневых комментариев минимум нескольких роликов и настоящих вложенных ответов с верными video/root/parent ID; счётчик `commentCount` не считается заменой            |
| Сомнительный replies `item_id` | Запрос/ответ проверены на ролике с видимыми ответами; если нужна правка, она минимальна, воспроизводима и изолирована, либо SDK отклоняется                                               |
| Пагинация и ограничения        | Отсутствуют cursor loops; ID не обрезаются; общий предел учитывает ответы и внутренние retries; отмена останавливает новые страницы                                                       |
| Повторный запуск               | После перезапуска worker сессия и checkpoint работают, результаты upsert по platform/entity ID, повтор не создаёт дублей; новые комментарии обнаруживаются отдельной политикой обновления |
| Повторяемость                  | Несколько запусков в разные дни в той же среде; разовый успех не объявляется стабильной интеграцией                                                                                       |
| Ошибка или challenge           | Остановка с различимым статусом и сохранением результата; пустой HTTP 200 не превращается в «0 комментариев»; повторные входы не запускаются автоматически                                |
| Бесплатный режим               | Опыт работает без обязательных платных proxy/SaaS/solver; иначе кандидат не проходит текущее требование                                                                                   |

Если TikTokApi не проходит, проверяем тот же контракт DTK в отдельном контейнерном сервисе с одним identity и ограниченной очередью. Поддержку больших пулов identities и планировщика не импортируем в приложение автоматически. DTK имеет более высокую стоимость развёртывания и обновления, зато не требует собственного форка внутренних signing-модулей, если обращаться к его публичному REST.

После допуска выбранный worker реализует узкий контракт `listRecentVideos(profile, limit)`, `listComments(video, cursor)`, `listReplies(video, root, cursor)` и `checkAccess()`. Источники, budgets, checkpoints, SQLite, raw evidence и state machine запуска принадлежат e-content; фронтенд не зависит от SDK. В цех передаются собранные данные и явная полнота, затем уже темы/идеи. Сбор и анализ повторяются независимо: закрытие панели не запускает заново загрузку или обработку.

Это план следующей проверки, а не выполненный live-тест. Бесплатный исходный код снижает стоимость разработки, но не создаёт официального стабильного контракта TikTok и не гарантирует отсутствие ограничений аккаунта. Если оба кандидата не проходят, автоматический бесплатный сценарий в текущей среде остаётся неподтверждённым; усложнять собственное расширение вместо признания этого ограничения не следует.
