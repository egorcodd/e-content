# Локальный Telegram-коннектор

Реализовано 16 ноября 2026 года. Пользовательская сессия MTProto, библиотека `teleproto@1.233.0`, Node.js 24. Бот и платные посредники не используются. Проверенные методы и ограничения: [исследование](../research/TELEGRAM-CONNECTOR.md).

## Запуск и вход

`start.cmd` / `npm run dev` запускают сайт на `127.0.0.1:5186` и API на `127.0.0.1:5187`. Vite передаёт `/api` локальному серверу. Для API отдельно есть `npm run server`. Статическая папка dist сама по себе не исполняет коннектор; preview предназначен для визуальной проверки.

В `/sources?platform=telegram` пользователь вводит api_id и api_hash собственного приложения с my.telegram.org → API development tools, затем номер, реальный код и, если включена, пароль 2FA. Длина кода берётся из ответа Telegram. Автоматической регистрации, вступления в каналы, отправки сообщений и платного fallback нет. Если сервер недоступен, вход не подменяется макетом.

При ограничении прямого соединения можно перед запуском задать `TELEGRAM_PROXY_URL`, например `socks5://127.0.0.1:7890` или HTTP CONNECT proxy. Системный HTTP-прокси не применяется автоматически к MTProto. Адрес не попадает в браузер. Сервер не читает переменные с префиксом VITE для секретов.

## Границы модулей

- `server/telegram.ts` — адаптер методов Telegram, код/SRP, разрешение канала и пагинация сообщений. DTO сохраняет курсор даже у служебных сообщений. Обсуждение определяется через GetDiscussionMessage, далее GetReplies использует ID корня в группе, а не ID поста канала.
- `server/telegram-account.ts` — единственная сессия, ограниченный по времени вход, проверка владельца браузерного сеанса, подтверждённое завершение сессии и cooldown после FLOOD_WAIT. Код и пароль живут только во время входа, не записываются в БД.
- `server/collection.ts` — один выполняющийся запуск, неизменный снимок конфигурации, проверка доступа и compile CollectionPlan, лимиты перед каждым RPC/страницей, отмена и сохранение частичного результата.
- `server/store.ts` — SQLite: снимки запусков, канонические записи, отдельные снимки записей и найденных идей каждого запуска. Повторное чтение статуса не выгружает тексты оснований. Сами идеи/записи выдаются постранично.
- `src/features/collection` — API-клиент, опрос состояния, идемпотентный запуск и перенос полученных идей в существующий IndexedDB через saveFoundIdea. Состояние серверного запуска не принадлежит панели или компоненту сцены.

Полный цикл получает Telegram, извлекает комментарии, объединяет записи, выделяет вопросы, сохраняет идеи и передаёт результат в Ядро. TikTok и историческая аналитика в этом запуске не помечаются выполненными. Галерея `/design-system` сохраняет независимую демонстрацию взаимодействий.

## Данные и ограничения

Для канала читаются публикации выбранного периода, затем их обсуждения за тот же период. Ссылка на конкретный старый пост позволяет читать его свежие комментарии; сам старый пост не сохраняется вне окна. Включение пересылок, ответов внутри веток, минимальная длина, типы данных, лимиты источника и общий бюджет применяются на сервере.

Лимиты просмотра страниц включают служебные и отфильтрованные сообщения: это ограничение объёма фактического чтения, а не обещание получить ровно N подходящих текстов. Публикации с пересекающимися ссылками и повторные комментарии хранятся без дублей по каноническому peer/message ID. У записи сохраняются текст, дата, ссылка, источник и связь с публикацией; у вложенного ответа — ID родителя. Авторские профили не собираются. Счётчики просмотров/реакций/репостов сохраняются только при включении счётчиков и при наличии поля в ответе, отсутствие не превращается в ноль.

Получение данных делает не более одного явно учтённого RPC за попытку и выдерживает выбранный приложением интервал 1 секунда. Это политика приложения, а не гарантированная квота Telegram. FLOOD_WAIT прерывает запуск, сохраняет уже полученное и запрещает повторные обращения до указанного времени, в том числе после перезапуска сервера. Вход и проверка собственной сессии имеют отдельные ограниченные повторы для миграции между DC; они не входят в счётчик запросов сбора.

Первичное выделение тем без внешней нейросети: вопросы с `?` из комментариев и первые строки постов источников «Поиск идей». Совпадающие нормализованные вопросы объединяются; семантически разные формулировки автоматически не объединяются. До 100 тем и 100 оснований на тему за запуск. Формат не угадывается: новые идеи попадают в «Неразобранное», пользователь выбирает видео/пост. Существующие статусы, избранное и папки сохраняются при дополнении оснований.

Участки «Темы», «Материалы», «Сбор», «Комментарии» и Ядро могут повторно работать с последним сохранённым снимком без нового обращения к Telegram. Новый сетевой сбор запускается только явно через Telegram или полный цикл. Идемпотентный ID защищает от повторного запуска при потере HTTP-ответа. Нельзя одновременно запускать второй сбор. Закрытие панели/страницы не отменяет worker. После остановки процесса сервера активный запуск становится interrupted; автоматического возобновления сетевых запросов нет.

Выгрузка Markdown из цеха содержит исходные посты/реплики, ссылки и доступные счётчики. Библиотека идей хранит темы и основания отдельно от технических данных. Исторические графики аналитики пока используют существующие локальные ряды: текущие публичные счётчики постов не заменяют историю подписчиков или источники просмотров.

## Хранение и доступ

`.local/content.sqlite` содержит собранные данные. api_hash и StringSession хранятся в зашифрованном vault AES-256-GCM; ключ — `.local/vault.key`, рядом с БД. Это защита от случайного раскрытия БД отдельно от ключа, не защита от пользователя с доступом ко всей папке. POSIX mode не является Windows ACL. Вся `.local/` и файлы сессий исключены из Git; файл ключа нельзя терять при переносе БД. Не предназначено для публичного/многопользовательского размещения.

API слушает только loopback, проверяет Host/Origin/Sec-Fetch-Site. Изменения требуют случайной HttpOnly SameSite Strict cookie и CSRF-токена. Ответы no-store, секреты не возвращаются. Действие «Отключить» сначала подтверждает auth.logOut в Telegram и только затем удаляет локальную сессию; ошибка сохраняет её для повтора. Источники, записи и идеи не удаляются.

## Проверки

`check:server` проверяет HTTP-защиту, динамический код, 2FA, ошибки/отключение, пагинацию служебных сообщений, ID корня обсуждения, вложенные ответы, дедупликацию, ограничения, отмену, FLOOD_WAIT, идемпотентность и перезапуск. Gateway подменяется тестовым адаптером: эти проверки не входят в настоящий аккаунт.

`check:source-validation`, `check:module-setup` проверяют форму и компоновку в Edge. `check:telegram-workshop` проходит браузером через настоящий локальный API и worker с тестовым Telegram-адаптером: вход, источник, запуск, закрытие панели, перезагрузка, экспорт и библиотека. Живой вход и чтение конкретного канала требуют пользовательских реквизитов и кода; без них не утверждается, что интеграция проверена на аккаунте.
