# TikTok: статистика, комментарии и отдельный аккаунт

После этого исследования реализован гостевой браузерный адаптер. Его фактические возможности, проверки и ограничения живого теста описаны в [архитектуре TikTok](../architecture/tiktok-public.md). Рекомендации ниже сохраняют контекст выбора; официальный OAuth и вход во второй аккаунт пока не реализованы.

Проверено **16 ноября 2026 года**. Это анализ для следующего этапа, не реализация и не живой тест: аккаунты не создавались, авторизация не выполнялась, видео пользователя не собирались, платные сервисы не подключались. Официальные продукты, разрешения, Sandbox и ограничения выпуска подробно разобраны в [TIKTOK-OFFICIAL-ACCESS.md](TIKTOK-OFFICIAL-ACCESS.md). Здесь — выбор способа, проверка open source и привязка к существующему backend e-content.

## Рекомендация

Одна карточка TikTok в источниках, два независимых способа доступа:

| Задача                                       | Первый вариант                                                                                     | Ограничение                                                                                                         |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Текущие показатели своего профиля/видео      | Login Kit Desktop + Display API; начать с Sandbox                                                  | Нужны приложение, разрешения и согласие владельца. Фактическую выдачу нужных scopes в Sandbox ещё надо проверить    |
| Тексты комментариев своих видео официально   | Accounts API в API for Business                                                                    | Отдельная заявка на доступ и одобрение. Display-токен этого не даёт                                                 |
| Ограниченная проверка публичных комментариев | Изолированное публичное чтение без входа; при требовании входа — отдельная сессия второго аккаунта | Неофициальный web-доступ, возможны CAPTCHA, неполные ответы и ограничения. Не подтверждён как рабочий в нашей среде |

Основания: [Display](https://developers.tiktok.com/docs/en/display-api-overview), [Sandbox](https://developers.tiktok.com/docs/en/add-a-sandbox), [Accounts access](https://business-api.tiktok.com/portal/docs/create-a-developer-app/v1.3), [owned comments](https://business-api.tiktok.com/portal/docs/get-comments-on-an-owned-video/v1.3).

Для основного сценария поиска идей приоритет — проверить доступ к **одному конкретному публичному ролику** и его репликам. Не начинать с обхода профилей, больших объёмов и регистрации нового аккаунта до выяснения, нужен ли вход.

## Что значит «прямое API»

`open.tiktokapis.com/v2/...` — документированный Display API с OAuth. `/api/comment/list/` на `www.tiktok.com` — внутренняя поверхность публичного сайта, которой пользуются web-сборщики. JSON в ответе второго адреса не делает его официальным developer API. В исходниках DTK определены отдельные маршруты корневых комментариев и ответов. [Display overview](https://developers.tiktok.com/docs/en/display-api-overview), [DTK endpoints](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/platforms/tiktok/endpoints.py).

Display возвращает `view_count`, `like_count`, `comment_count`, `share_count`. Подписчики требуют `user.info.stats`. Эти поля описывают текущий снимок. Тексты реплик в Display не предусмотрены. Авторизовать второй аккаунт и запросить официальный video/query для ролика первого не получится: метод проверяет принадлежность видео. [Video Object](https://developers.tiktok.com/docs/en/tiktok-api-v2-video-object), [Get User Info](https://developers.tiktok.com/docs/en/tiktok-api-v2-get-user-info), [Video Query](https://developers.tiktok.com/docs/en/tiktok-api-v2-video-query).

Для локального Desktop callback допускается HTTP loopback и предусмотрен PKCE. Production review отдельно исключает private/personal-use приложения, поэтому нельзя представлять Sandbox как обещание постоянного production-доступа. Наличие всех необходимых scopes в созданном Sandbox нужно подтвердить в кабинете и реальным ответом API. [Desktop Login Kit](https://developers.tiktok.com/docs/en/login-kit-desktop), [App Review Guidelines](https://developers.tiktok.com/docs/en/app-review-guidelines).

Прямой официальный доступ позволяет обойтись без платного scraper-посредника. Проверенные страницы не дают основания обещать любой Accounts API безусловно бесплатным и доступным: условия его выдачи проверяются отдельно. Бесплатная OSS-библиотека тоже не гарантирует, что TikTok будет обслуживать её запросы. [Accounts access](https://business-api.tiktok.com/portal/docs/create-a-developer-app/v1.3), [TikTok-Api README](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/README.md).

## Второй аккаунт: что он решает

Он может быть самостоятельным читателем того, что TikTok показывает обычному зрителю: публичных роликов основного профиля и доступных обсуждений. Это архитектурный сценарий для проверки, а не доказанный результат в e-content. Он не становится владельцем чужого видео, не получает закрытую статистику основного профиля и не открывает скрытые владельцем комментарии через обычный публичный просмотр. Для официального метода owned comments требуется доступ владельца. [Video Query](https://developers.tiktok.com/docs/en/tiktok-api-v2-video-query), [Owned comments](https://business-api.tiktok.com/portal/docs/get-comments-on-an-owned-video/v1.3).

Предлагаемая изоляция: отдельный каталог/контекст браузера, ручной вход пользователя только на сайте TikTok, показ фактически вошедшего `@username` перед сохранением сессии. Не использовать обычный Chrome-профиль пользователя и не импортировать cookies основного аккаунта. OAuth-токен для статистики и browser storage для чтения — разные секреты с разными ролями; автоматически не переносить их между адаптерами. `msToken`, получаемый гостевой web-сессией, сам по себе не означает вход в пользовательский аккаунт: библиотека допускает создание сессий без предоставленного токена и отдельно принимает cookies. [TikTok-Api session implementation](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/tiktok.py), [Playwright authentication](https://playwright.dev/docs/auth).

Изоляция означает, что наш сборщик не получает основную сессию. Она не доказывает, что TikTok никогда не свяжет действия или не ограничит доступ по другим признакам. Публичной гарантии «второй аккаунт исключает блокировку основного» нет. ROW Terms запрещают автоматизированный сбор; применимые условия зависят от региона. TikTok разрешает несколько аккаунтов, но запрещает использовать другой для обхода действующих ограничений. Поэтому смена аккаунта при блокировке не является предлагаемой стратегией восстановления. [Terms §5](https://www.tiktok.com/legal/page/row/terms-of-service/en), [Account restrictions](https://support.tiktok.com/en/safety-hc/account-and-user-safety/content-violations-and-bans).

## Что показал просмотр open source

HEAD закреплён через GitHub API в момент исследования; выводы ниже получены из кода, не из собственного успешного сбора.

### davidteather/TikTok-Api

Commit `c5600f9ca8a411e93638e984407d41cca4209cb4`. Компактный Python-клиент с Playwright, кандидат для сравнительной проверки. README прямо описывает блокировку запросов через EmptyResponseException и изменчивость сайта. Рекламные ссылки на платных поставщиков не являются обязательным использованием этих поставщиков. [README](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/README.md).

`Video.comments(count=...)` запрашивает страницы по 20 и проверяет общий счётчик только в условии внешнего цикла: выдача может превысить небольшой остаток нашего лимита. Нет достаточного общего предохранителя от повторяющегося cursor/пустых страниц с has_more. В `Comment.replies()` item_id заполнен user_id автора комментария, а не ID ролика — это подозрительная привязка, которую нельзя считать исправной без отдельной проверки. [video.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/api/video.py), [comment.py](https://github.com/davidteather/TikTok-Api/blob/c5600f9ca8a411e93638e984407d41cca4209cb4/TikTokApi/api/comment.py).

Вывод: не подключать высокоуровневый генератор напрямую к нашим лимитам. Если выбирать библиотеку — оборачивать постраничным адаптером, закреплять версию, проверять replies и считать реальные попытки запросов, включая внутренние retries. Сам `msToken` не заменяет подтверждение доступности комментариев.

### Evil0ctal/DTK v5

Commit `3c045e11aecd58ab076562f1246931b9dd5d909b`. Self-hosted сервер; текущая v5 существенно отличается от старых инструкций v4. В составе есть PostgreSQL/Redis, браузерная инфраструктура и своя консоль. Для существующего небольшого Node/SQLite backend e-content это дополнительный обслуживаемый сервис. [Repository](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/tree/3c045e11aecd58ab076562f1246931b9dd5d909b).

Сильная сторона для изучения — явная модель страниц/ошибок: отдельные комментарии и ответы, обязательный cursor при has_more, nullable отсутствующие метрики и строковые длинные ID. Наличие маршрута и parser не подтверждает доступность конкретного видео. [Parser](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/platforms/tiktok/parser.py), [Models](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/3c045e11aecd58ab076562f1246931b9dd5d909b/src/dtk/models/content.py).

Вывод: резервный кандидат для сравнения. Не переносить весь стек, его пулы идентичностей и консоль в e-content только ради чтения одного ролика; не наследовать автоматические повторы/смену идентичностей как нашу политику.

### Собственный ограниченный browser-reader

В проекте уже установлен Node Playwright для UI-проверок. Его можно использовать в изолированном серверном модуле, но готового TikTok-парсера он не предоставляет. Предлагаемый первый прототип: видимый обычный браузер, выбранный ролик, чтение доступного содержимого и ответов страницы, явная остановка при требовании входа/проверке. Это инженерная рекомендация по управляемости и отсутствию Python-сервиса, а не обещание стабильности или разрешения TikTok. Сессионное состояние требует закрытого хранения. [Playwright](https://playwright.dev/docs/intro), [Authentication](https://playwright.dev/docs/auth).

## Как подключать к нашей архитектуре

Это проект изменения; перечисленные модули пока не написаны.

1. **Разделить адаптеры.** `tiktok/display` — официальный OAuth/снимки; `tiktok/public-reader` — публичные реплики; `tiktok/accounts` — опциональный официальный путь комментариев после одобрения. UI показывает доступность статистики и комментариев независимо. Статус OAuth не означает, что сбор реплик работает.
2. **Обобщить существующий Telegram DTO.** Сейчас CollectedRecord жёстко использует platform=telegram, peerId и числовой messageId. Нужна нормализация на границе адаптера: строковые contentId/commentId/parentId, nullable даты/метрики, provider и observedAt. Существующие записи Telegram мигрируют без потери связей и IDs. Длинные TikTok ID никогда не проходят через JS Number. app-scoped OAuth open_id нельзя приравнивать к публичному numeric user ID. Модель adapter capabilities в collection-policy.ts уже даёт основу проверки возможностей.
3. **Разделить привязки.** Сейчас у источника один accountId. Для двух способов доступа нужен явно выбранный statsConnection и commentsConnection либо таблица назначений по capability. Миграция сохраняет прежние источники; права одной сессии не подставляются другой автоматически.
4. **OAuth callback проектировать отдельно.** В текущем server/index.ts общие API отклоняют Sec-Fetch-Site=cross-site, а ec_local имеет SameSite=Strict. Обычный возврат с TikTok поэтому нельзя просто добавить в общий обработчик. Нужен узкий callback с одноразовым state/PKCE, сроком и привязкой к начавшему вход браузеру; возможный вариант — отдельная краткоживущая HttpOnly SameSite=Lax cookie только для OAuth. Остальные API сохраняют существующую защиту. Секрет приложения, токены и коды не попадают в URL логов или клиентский bundle; после callback выполняется переход на чистый адрес.
5. **Исполнитель не зависит от UI.** Подключить TikTok через общий контракт страниц и возможностей, сохранить одного worker, идемпотентный ID, явный запуск и отмену. Учитывать отдельно запросы данных и весь сетевой трафик браузера: загрузка страницы порождает дополнительные обращения. Не объявлять один вызов генератора одним запросом. После закрытия браузера/цеха состояние и уже сохранённые записи остаются в SQLite.
6. **Точность сбора.** Сохранять текст, исходный ролик, ID, дату при наличии, parent/root связь и лайки комментария. Встроенные previews ответов и полные страницы дедуплицировать по ID. Публичный счётчик comment_count не доказывает, что столько же текстов доступно сборщику. has_more=false означает конец выданного набора, не доказательство получения всех скрытых/удалённых комментариев.
7. **Фильтры без выдуманной хронологии.** Окно 7/30/90 фильтрует сохранённые даты, но обход нельзя заканчивать на первом старом комментарии без гарантии порядка. При достижении лимита помечать результат как ограниченный объёмом. Отсутствующая дата не становится сегодняшней; неизвестные лайки не становятся нулём для фильтра minLikes.
8. **Аналитика — отдельные снимки.** Хранить account/video ID, provider, время, nullable счётчики и покрытие периода. Приоритет у официального источника, публичные наблюдения помечаются отдельно. Исторические графики накапливаются с момента наблюдения; разность счётчиков отражает наблюдаемое изменение и возможные корректировки, а не гарантированную внутреннюю отчётность TikTok. Текущие mock-ряды аналитики не смешивать с реальными без явной смены источника данных.

## Минимальный опыт перед выбором адаптера

- Один выбранный пользователем публичный URL, первый запрос корневых комментариев, ориентир 20–50 реплик; вложенные ответы проверять отдельно. Это наш экспериментальный предел, не безопасная квота TikTok.
- Сначала без входа; проверить, что нужные реплики вообще видны в обычном браузере. Гостевые cookies допустимы; основной аккаунт в эксперименте не участвует.
- Если требуется вход, сохранить отдельный статус и предложить пользователю ручной вход во второй аккаунт. Не регистрировать аккаунты и не переключать их автоматически.
- На CAPTCHA, 401/403/429, пустом/непонятном ответе, повторном cursor — остановка, сохранение уже полученного и причины. Нет автоматического решения CAPTCHA или повтора через другие аккаунты.
- Проверить корневой комментарий и ответ вручную, дату, текст, принадлежность ролику и отсутствие дублей. Повторить разрешённое чтение позднее, не называть один успех гарантией стабильности.
- Первый опыт полностью локальный. Нет ключей платных API, оплачиваемых прокси/решателей или автоматического fallback на облачный scraper. Если бесплатный путь не работает, результат — понятная ошибка/частичные данные, не внезапный счёт.

Решение после опыта: рабочий публичный reader, официальный Accounts путь при выданном доступе либо импорт разрешённого файла. Автоматически считать, что личный архив TikTok содержит все входящие комментарии, нельзя.
