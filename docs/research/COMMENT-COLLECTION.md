# Сбор комментариев и поиск тем для e-content

Актуальное дополнение от 16 ноября 2026 года: [план TikTok-коннектора и отдельный аккаунт](TIKTOK-CONNECTOR-PLAN.md), [официальные разрешения TikTok](TIKTOK-OFFICIAL-ACCESS.md). Ниже сохранено первоначальное исследование; Telegram с тех пор реализован в [локальном коннекторе](../architecture/telegram-local.md).

Проверено **15 ноября 2026 года**. Изучены официальные API, документация, исходный код, лицензии и сообщения об ошибках. Это исследование и проект внедрения: аккаунты не авторизовывались, библиотеки не устанавливались, платные сервисы не запускались, комментарии пользователя не собирались.

## Вывод для проекта

**Собственный сбор без оплаты за каждый комментарий технически возможен.** Для Telegram есть документированный пользовательский API; для TikTok существуют self-hosted проекты. Однако нельзя обещать гарантированное получение всех комментариев TikTok на любом сервере: публичный сайт может возвращать неполные страницы, требовать вход или блокировать автоматические обращения. Наличие open source этого не отменяет.

Практический порядок: Telegram через пользовательский MTProto-клиент; параллельно ограниченная проверка TikTok на нескольких своих публичных роликах; затем выбор адаптера по результатам проверки. Платный сборщик не нужен как обязательная зависимость. Основной конвейер анализа должен принимать данные от разных адаптеров и из импортированного файла.

## 1. Telegram через свой аккаунт

### Что действительно доступно

Пользовательский Telegram API позволяет постранично читать историю доступного чата/канала через `messages.getHistory`. Администратором для обычного чтения доступной истории быть не требуется. Приватный или недоступный канал может вернуть `CHANNEL_PRIVATE`; собственная авторизация не даёт доступ к чужим закрытым чатам. [getHistory](https://core.telegram.org/method/messages.getHistory).

Комментарии канального поста связаны с веткой в группе обсуждения. Для них есть `messages.getReplies`; он доступен пользовательским аккаунтам и поддерживает offsets, limit и диапазоны ID. Нужно сохранять связь исходного поста, discussion peer и сообщений ветки, а не воспринимать все сообщения группы как комментарии к одному посту. [Message threads](https://core.telegram.org/api/threads), [getReplies](https://core.telegram.org/method/messages.getReplies), [getDiscussionMessage](https://core.telegram.org/method/messages.getDiscussionMessage).

Посты, доступные комментарии, даты и связи ответов можно использовать как вход для поиска повторяющихся вопросов. Счётчики просмотров, пересылок и реакций относятся к сообщению; административная аналитика канала — отдельная возможность, не обязательная для чтения текстов. [Message](https://core.telegram.org/constructor/message), [Channel statistics](https://core.telegram.org/api/stats).

Для пользовательской авторизации нужны свои `api_id`/`api_hash` из API development tools и вход владельца аккаунта. Telegram предлагает API без платы за прочитанное сообщение. Ограничения частоты при этом действуют. [Creating your Telegram application](https://core.telegram.org/api/obtaining_api_id).

### Чтение и AI-анализ — разные разрешения

Техническая доступность сообщения не означает разрешение на любое дальнейшее использование. Актуальный §1.5 Telegram API Terms и Content Licensing ограничивают использование данных для AI/ML, включая deployment, а не только обучение. Content Licensing описывает исключение при явном, информированном и продолжающемся согласии всех соответствующих пользователей для конкретного контекста. Нельзя считать одного входа Егора достаточным согласием всех авторов комментариев или чужого канала. Перед автоматическим AI-анализом таких данных нужно определить допустимый сценарий и основания/согласия; локальный LLM сам по себе не снимает это условие. [API Terms](https://core.telegram.org/api/terms), [Content Licensing](https://telegram.org/tos/content-licensing).

## 3. Open source и собственный запуск TikTok

### TikTokApi от David Teather

Python-проект с лицензией MIT. В исходниках действительно реализованы `Video.comments()` и `Comment.replies()`: cursor/has_more, ID, текст, лайки, сырой ответ. Это не просто библиотека скачивания видео. [Video source](https://github.com/davidteather/TikTok-Api/blob/main/TikTokApi/api/video.py), [Comment source](https://github.com/davidteather/TikTok-Api/blob/main/TikTokApi/api/comment.py), [License](https://github.com/davidteather/TikTok-Api/blob/main/LICENSE).

README ограничивает библиотеку публичными маршрутами, доступными без входа, и прямо исключает user-authenticated routes. Пример использует браузерную сессию и `msToken`; это не официальный OAuth владельца. README также описывает пустые ответы при обнаружении автоматизации. [Repository](https://github.com/davidteather/TikTok-Api).

Наблюдения из прочитанного кода, которые нужно проверять до интеграции:

- `count` проверяется между страницами, но внутри страницы записи выдаются целиком. Внешний потребитель должен сам останавливать чтение на строгом лимите.
- Нужны ограничения числа страниц, повторяющегося cursor и пустых страниц с `has_more=true`, иначе один только счётчик полученных записей не гарантирует завершения.
- В `replies()` параметр `item_id` заполняется `author.user_id`; это подозрительное место привязки к ролику. Работоспособность ответов нельзя считать доказанной только по наличию метода.

Это анализ [video.py](https://github.com/davidteather/TikTok-Api/blob/main/TikTokApi/api/video.py) и [comment.py](https://github.com/davidteather/TikTok-Api/blob/main/TikTokApi/api/comment.py), не результат живого теста. Есть открытое сообщение о неработающем извлечении комментариев; старый закрытый issue о пагинации не доказывает исправность текущей среды. [Issue #1255](https://github.com/davidteather/TikTok-Api/issues/1255), [старый #926](https://github.com/davidteather/TikTok-Api/issues/926). Репозиторий и CI продолжают изменяться, но их наличие не гарантирует совместимость с TikTok. [Actions](https://github.com/davidteather/TikTok-Api/actions).

**Оценка:** хороший небольшой кандидат для первой ограниченной проверки; не готовая гарантия полного сбора.

### Douyin_TikTok_Download_API / DTK

Текущий проект Evil0ctal — self-hosted сервер с Apache-2.0, REST/MCP и своей консолью. README заявляет TikTok comments и replies; исходный `EndpointTable` действительно регистрирует оба маршрута. Это не ссылка на обязательный платный API. [Repository](https://github.com/Evil0ctal/Douyin_TikTok_Download_API), [endpoint source](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/src/dtk/platforms/tiktok/endpoints.py), [License](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/LICENSE).

Парсер отдельно обрабатывает ответы комментариев, а слой параметров и сессий зависит от текущего web-поведения TikTok. Считать проект устойчивым только по числу звёзд нельзя. [Parser](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/src/dtk/platforms/tiktok/parser.py), [params](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/src/dtk/platforms/tiktok/params.py).

У v5 уже есть PostgreSQL/Redis и браузерная инфраструктура, то есть он тяжелее узкого worker. Использовать его как изолированный адаптер можно после проверки минимального сценария, не переносить целиком чужую консоль в e-content. Текущий `main` существенно отличается от v4; старые пути `crawlers/...` неприменимы к новой версии. [Architecture / versions](https://github.com/Evil0ctal/Douyin_TikTok_Download_API), [project summary](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/llms.txt).

**Оценка:** второй кандидат для сравнительной проверки, особенно если небольшой TikTokApi не справится; пока не развёрнут и не проверен на видео Егора.

### Playwright и Crawlee

Playwright — управление браузером, Crawlee — очередь и исполнение crawler-задач. Они не содержат готовой гарантии извлечения TikTok-комментариев: собственный обработчик страницы всё равно нужен. Crawlee позволяет ограничить concurrency, retries, requests и timeout. [Playwright](https://playwright.dev/docs/intro), [Crawlee options](https://crawlee.dev/js/api/playwright-crawler/interface/PlaywrightCrawlerOptions).

Обе библиотеки имеют Apache-2.0 и могут исполняться локально. Crawlee не тождественен платному запуску Actor в облаке Apify: quick start устанавливает пакет и сохраняет результаты в локальную `storage`. [Crawlee quick start](https://crawlee.dev/js/docs/quick-start), [Crawlee license](https://github.com/apify/crawlee/blob/master/LICENSE.md), [Playwright license](https://github.com/microsoft/playwright/blob/main/LICENSE).

Сохранённое состояние браузера может содержать чувствительные cookies и заголовки. Если выбран сценарий входа, пользователь авторизуется в отдельном профиле, а файл состояния не попадает в репозиторий и клиентский bundle. При CAPTCHA/запрете/истекшей сессии задача останавливается с понятным состоянием. Обходы проверок и платные CAPTCHA-сервисы в предлагаемый MVP не входят. [Authentication](https://playwright.dev/docs/auth).

**Оценка:** разумный собственный адаптер с контролем пользовательского входа, если готовые проекты не подходят; выше стоимость поддержки интерфейса.

### Почему не выбираем первый попавшийся старый scraper

TikTokPy тоже существует, однако его исходный сопровождающий описывал проблемы и отсутствие времени на поддержку. Старое исправление или успешный пример не является актуальным smoke-test. Он не выбран основой без дополнительной проверки. [Project](https://github.com/Russell-Newton/TikTokPy), [maintainer response](https://github.com/Russell-Newton/TikTokPy/issues/83).

OSS-лицензия разрешает использование кода в своих условиях, но не заменяет условия площадки и разрешения на данные. TikTok Terms содержат ограничение автоматизированного сбора; конкретный допустимый способ интеграции следует выбирать с учётом условий аккаунта и региона. Нельзя описывать неофициальный web-сбор как официально одобренный TikTok API. [TikTok Terms, §5](https://www.tiktok.com/legal/page/row/terms-of-service/en).

## 4. Как исключить случайный счёт за сбор

Ниже **предлагаемая политика нашего приложения**, пока не реализованная. Это не лимиты Telegram/TikTok и не обещание чужого провайдера.

1. **Платные коннекторы выключены по умолчанию.** Нет ключей Apify/TikAPI/прокси-провайдеров, нет автоперехода на платный сервис при ошибке бесплатного. Наличие названия поставщика в настройках не включает оплату.
2. **Строгие лимиты задаёт наш сервер до каждого запроса**, а не LLM и не параметр `count` сторонней библиотеки. Счётчик общий для основной задачи и ответов, reservations сохраняются до отправки запроса, включая retries.
3. Предварительный безопасный профиль: максимум **3 ролика**, **200 верхних комментариев на ролик**, **50 ответов на ветку**, **1000 записей суммарно с ответами**, **60 страниц/обращений за задачу**, **5 минут**, **1 одновременный сборщик**. Срабатывает первый достигнутый предел. Числа можно изменить позже после замеров.
4. Задача работает только по явно выбранным URL/каналам. Нет обхода всех найденных ссылок, автоподписки на каналы, скрытых расписаний и бесконечных повторов.
5. Одинаковый cursor, повторно пустые страницы, отсутствие новых ID, ошибка доступа, CAPTCHA или FloodWait приводят к остановке/отложенному возобновлению, а не к безлимитному циклу. Отмена обрывает дочерние запросы и worker по deadline.
6. Собственный сбор не имеет тарифа за комментарий, но остаются расходы на уже выбранный VPS, трафик и хранение. Для эксперимента не покупать ресурсы автоматически; установить CPU/RAM/дисковые квоты.
7. **LLM-анализ — отдельная статья затрат.** Отключён до настройки; фиксированный model allowlist, лимиты входа/выхода и запросов, кэш и журнал расхода. Дешёвый сбор не означает бесплатный внешний анализ. Для действительно локального режима возможна локальная модель; серверные предупреждения о бюджете не считать гарантированным жёстким ограничением провайдера.

Если платный адаптер когда-либо понадобится, выбирать его отдельно, с заранее заданным пределом расходов и проверенным поведением остановки у провайдера. Текущая рекомендация обходится без него.

## 5. Архитектура минимального рабочего конвейера

Это проект следующего серверного этапа, не описание уже работающего backend.

```text
Выбранные каналы / URL роликов
  → задача сбора с фиксированными лимитами
  → Telegram adapter / TikTok adapter / импорт JSON, CSV
  → нормализация, удаление дублей и checkpoint
  → хранилище реплик и связей
  → анализ разрешённых данных
  → темы и идеи с основаниями
  → Markdown в библиотеке
```

- **Сайт:** запускает, отменяет и показывает фактический прогресс; не получает cookies, Telegram session или client secrets.
- **Worker:** отдельный процесс/контейнер с выбранным адаптером. Не давать модели возможность самой снимать ограничения или авторизовывать платный fallback.
- **Контракт комментария:** platform, source/account, channel/video ID, comment ID как строка, parent/thread ID, текст, дата, likes/reactions, source URL, fetched_at, adapter/version и сведения о доступности. Для Telegram ID сообщения уникален вместе с peer ID, не глобально.
- **Хранение:** структурированная БД для реплик/задач/cursors, Markdown для результата. Дедупликация по `(platform, source_id, comment_id)`. Повторный сбор обновляет редактирования и счётчики, не создаёт новые копии.
- **Checkpoint:** source, cursor/offset, последние ID, счётчики лимитов и причина остановки. Новые комментарии могут появиться в старом посте, поэтому одного «последнего поста» недостаточно; нужны выборочный повторный просмотр веток и перекрывающееся окно.
- **Полнота:** `partial`, `limit_reached`, `blocked`, `access_denied`, `cancelled`, `finished_available_pages`; число видимых/загруженных реплик отдельно от счётчика платформы. Завершение пагинации не доказывает существование всех удалённых/скрытых комментариев в выгрузке.
- **Идеи:** исходные цитаты и ссылки, повторяемость вопроса, число разных авторов внутри разрешённой выборки, свежесть и обсуждение. Чётко отличать наблюдаемый запрос аудитории от вывода модели. Имя автора не требуется в тексте итоговой идеи.

## 6. Проверка перед выбором TikTok-адаптера

1. На разрешённых данных: свой публичный ролик с небольшой веткой, ролик с ответами и ролик с большим обсуждением.
2. Сравнить полученный текст и parent IDs с доступным интерфейсом. Проверить Unicode, emoji/нетекстовые комментарии, даты и несколько страниц.
3. Остановить на лимите, отменить посреди чтения, перезапустить с checkpoint и убедиться, что нет дублей и увеличения зарезервированного бюджета.
4. Проверить истекшую авторизацию, недоступный ролик, пустую страницу и повторный cursor. Нет данных — отдельное состояние, не успешная пустая выгрузка.
5. Повторить на локальной машине и предполагаемом VPS. Успех на одном IP/в один день не гарантирует успех на другом окружении завтра.
6. Зафиксировать точную версию/commit и условия успешного опыта. Только после этого назвать выбранный способ рабочим для e-content.

Для импорта JSON/CSV можно реализовать тот же анализ и библиотеку без сетевого TikTok-коннектора. Это резервный способ продолжить работу на корректно полученных файлах, а не обещание, что личный архив TikTok обязательно содержит все входящие комментарии.

## 7. Конкретная интеграция после страницы материалов

Дополнение проверено **15 ноября 2026 года** по текущему `main` DTK. Ниже разделены существующие контракты стороннего проекта и предлагаемый контракт e-content. Ничего из этого дополнения не устанавливалось и не подключалось.

### Существующий REST-контракт DTK v5

| Операция           | Путь                                        | Минимальные параметры                                |
| ------------------ | ------------------------------------------- | ---------------------------------------------------- |
| Комментарии TikTok | `GET /api/v1/tiktok/video/comments`         | `url` **или** `aweme_id`; затем `cursor`, `count`    |
| Ответы             | `GET /api/v1/tiktok/video/comments/replies` | Тот же ролик и `comment_id`; затем `cursor`, `count` |
| Результат задачи   | `GET /api/v1/tasks/{task_id}`               | ID ранее отправленной задачи                         |

Маршруты подтверждены [исходником content routes](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/src/dtk/api/routes/content.py). `sort=new` для TikTok не поддерживается; использовать порядок, который отдаёт площадка. Вызов проверяет параметры и обычно возвращает `202` с задачей; после её завершения worker получает страницу. Повторное ожидание результата не означает повторную отправку задачи. Ключ с `tiktok:read` хранится в нашем backend, не в браузере; `admin` для чтения не нужен. [REST guide](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/documents/en/11-api.md).

Нормализованный результат — `Page<Comment>`: `items`, непрозрачный строковый `cursor`, `has_more`. Комментарий содержит строковые `comment_id`, `content_id`, `parent_id`, `text`, nullable `created_at`, `digg_count`, `reply_count`, автора и дополнительные признаки. Не преобразовывать длинные ID в JavaScript `number`; отсутствие метрики не заменять нулём. [Модели DTK](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/src/dtk/models/content.py).

Наш адаптер должен извлекать страницу из фактической оболочки завершённой задачи, сохранять результат и checkpoint одной транзакцией, затем применять собственный лимит перед следующей страницей. Версию DTK фиксировать по release/commit и проверять против её OpenAPI: движущийся `main` не является стабильной зависимостью.

### Выбор минимального исполнения

| Вариант                       | Что добавляется к e-content                                                                                  | Когда выбирать                                                                                              |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| **Свой небольшой worker**     | Очередь задач, Telethon для Telegram; отдельный TikTok-адаптер после smoke-test; общая БД/файлы и лимиты     | Предпочтительный старт: один аккаунт, выбранные источники, только тексты                                    |
| **DTK v5 как частный сервис** | Его API/worker, PostgreSQL/Redis и браузерная инфраструктура; наш backend вызывает только нужные REST-методы | Если проверка покажет, что DTK даёт полезный и стабильный результат и оправдывает дополнительные компоненты |

Собственный worker не означает переписывание криптографии Telegram или собственный браузерный движок. Он ограниченно использует проверенные библиотеки. При DTK его консоль, скачивание медиа и транскрибация не становятся частью нашего интерфейса автоматически; сетевой доступ к сервису закрыт от публичного интернета. Платных ключей и автоматического платного fallback в обоих вариантах нет. Оценка сложности основана на [структуре DTK](https://github.com/Evil0ctal/Douyin_TikTok_Download_API) и уже разобранных возможностях библиотек; это рекомендация проекта.

Для Telegram минимальная последовательность: авторизация своей пользовательской сессии → явно выбранные доступные каналы → ограниченная история постов → доступные ветки через `messages.getReplies` → общий контракт комментария. Список разрешённых каналов, period/limit и отмена задаются нашим исполнителем, не моделью. Историю и обсуждения читать документированными MTProto-методами, а не парсить Telegram Web. Условия использования данных из раздела 1 продолжают действовать. [getHistory](https://core.telegram.org/method/messages.getHistory), [getReplies](https://core.telegram.org/method/messages.getReplies).

### Контракт e-content, независимый от поставщика

Предлагаемый внутренний интерфейс адаптера: `fetchPosts(source, cursor, limit)` и `fetchComments(source, post, parentId?, cursor, limit)` → `{ items, nextCursor, hasMore, fetchedAt, completeness, warnings }`. Это **наш проект**, а не существующие имена методов DTK/Telethon. Адаптер не сохраняет материалы и не запускает LLM; этим управляет общий исполнитель.

Материал хранит внутренний UUID, исходную платформу/URL/ID, тип, заголовок, Markdown, ссылки на исходные реплики, статус и время сохранения. Отчёт и исходные комментарии имеют отдельные ID. Сохранение результата и чтение уже сохранённого материала не требуют живого TikTok-запроса. Страница материалов сначала работает с этим хранилищем; интеграция источников добавляется позже без изменения её основного контракта.

## 8. MCP позже: читать сохранённое, не управлять аккаунтами

MCP — интерфейс доступа агента к нашим данным и инструментам; сам по себе он не даёт доступ к Telegram/TikTok. Для первого этапа предлагается **свой узкий MCP над хранилищем e-content**, без запуска сбора. Страница материалов и сохранение работают независимо от MCP.

Предлагаемые инструменты: `materials.list` с фильтрами и cursor, `materials.get` по внутреннему ID, `comments.list` по ID материала/источника и `runs.get` для состояния существующей задачи. Ограниченные JSON Schema входа/выхода, page size максимум 100, проверка владельца и scope на сервере. `readOnlyHint: true` описывает чтение архива; это подсказка, не механизм авторизации. Не добавлять инструменты произвольного чтения пути, запуска shell, cookies, авторизации, публикации и изменения настроек. Основа протокола — официальный [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) и [ToolAnnotations schema](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts); сами имена инструментов и пределы выше — предложение e-content.

Если позднее появится инструмент `collection.start`, он создаёт задачу и пишет в БД: его нельзя выдавать за полностью read-only. Он принимает только разрешённый source ID и уже заданный профиль лимитов, а не произвольные URL/бюджеты/ключи от модели. Для начала такой инструмент вообще не нужен.

Для локального subprocess возможен stdio с секретами из окружения. Для защищённого удалённого HTTP MCP официальный профиль описывает OAuth, resource metadata, scope и проверку токена; токен e-content не является Telegram session или TikTok cookies. Не пересылать провайдерские credentials агенту и не считать подсказки `readOnlyHint` достаточной защитой. [MCP Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization). Перед реализацией фиксировать совместимые версии SDK/протокола: текущая спецификация — `2026-07-28`, старые примеры `initialize`/сессий могут относиться к другой версии.

У самого DTK уже есть `/mcp/`, но его `list_comments` отдаёт **только верхние комментарии**; ответы под ними доступны через REST, не через этот набор MCP-инструментов. Поэтому подключение DTK MCP само по себе не закрывает наш сценарий веток. Для нашего интерфейса предпочтителен REST-адаптер и собственный контролируемый доступ к архиву; прямой DTK MCP можно рассмотреть отдельно после проверки. [DTK MCP guide](https://github.com/Evil0ctal/Douyin_TikTok_Download_API/blob/main/documents/en/12-mcp.md).
