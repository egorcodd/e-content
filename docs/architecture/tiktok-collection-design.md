# Сбор TikTok для цеха идей

Цех использует публичное подключение TikTok. При подключённом ключе «Собрать идеи» и «Запустить весь цикл» автоматически передают выборку комментариев в ИИ. Отдельный дозабор веток пополняет локальную библиотеку.

## Данные одного запуска

Кнопка TikTok запускает сбор обсуждений выбранного профиля, разбор, публикацию материалов и отчёт ядра. Кнопка Telegram выполняет те же этапы для выбранных каналов. Полный цикл включает оба включённых источника и отдельный замер аналитики. Периодический замер выполняется при работающем свободном сервере, по умолчанию через сутки.

На сбор комментариев TikTok отведено до пяти минут с начала этапа TikTok. Пауза площадки завершает чтение раньше. После этого цех один раз разбирает доступные новые тексты, сохраняет идеи и завершает запуск. При пустой выборке запрос к модели пропускается. Следующее нажатие с теми же параметрами продолжает выбранные ролики с сохранённых страниц. Список роликов, позиции веток и идентификаторы реплик переживают перезапуск сервера. Отчёт и список реплик, переданных модели, сохраняются вместе.

В SQLite таблица `records` хранит полученные реплики между запусками. Таблица `run_records` фиксирует состав конкретной выборки. Сохранение новой реплики и её включение в запуск атомарны. Курсоры страниц и сроки ожидания площадки ведутся отдельно.

Цех сначала добавляет свежие реплики, затем заполняет свободные места сохранёнными. Действуют выбранный источник, список роликов, период, включение ответов, фильтр лайков и лимиты. При паузе обновления каталога доступен последний подтверждённый список подключённого профиля. В отчёте указываются происхождение списка и число добавленных из библиотеки реплик. Покрытие свежего сбора учитывается отдельно.

ИИ получает зафиксированную выборку. Для одинакового входа используется уже сохранённый ответ. Явный отказ сервиса принять запрос позволяет повторить попытку после исправления причины. Если связь оборвалась и факт исполнения неизвестен, автоматическое повторное списание заблокировано. В тот же запрос входят заголовки, планы и идентификаторы тем из предыдущих отчётов. Модель сопоставляет вопрос аудитории и ответ, который должен дать автор. Для дополнения существующей темы достаточно одной новой проверенной цитаты. Для новой темы по комментариям нужны независимые ветки. Сервер проверяет идентификатор темы и дословность цитат, затем объединяет основания по идентификатору реплики. Отчёты запусков сохраняются отдельно от общего списка карточек.

## Выбор источника для своего аккаунта

Для роликов автора первым кандидатом служит **TikTok API for Business → Organic API → Accounts API**. Платформа описывает управление собственным присутствием автора, модерацию комментариев и анализ публикаций. С марта 2026 года для нового приложения с правами TikTok Accounts требуется заявка на доступ. В заявке цеху следует прямо описать отбор тем из обсуждений, хранение оснований и экспорт. Уровни аккаунта различаются. Доступ приложения и аккаунта `@egorcod` к этим операциям предстоит подтвердить при авторизации. Переводить личный аккаунт в другую категорию до проверки преждевременно. [Возможности, типы аккаунтов и условия допуска](https://business-api.tiktok.com/portal/docs/accounts-api-overview/v1.3)

1. **Первичный сбор.** После согласия владельца получить список его роликов через `/business/video/list/`, загрузить публичные комментарии через `/business/comment/list/` с `status=PUBLIC` и `include_replies=true`. Вместе с корневым комментарием TikTok может вернуть до трёх ответов. Остаток ветки доступен отдельными страницами. При обходе учитывать `has_more`, сохранять ID строками и устранять дубли. После первых 500 комментариев к ролику порядок сортировки меняется, поэтому первая старая запись не доказывает, что дальше нет свежих. [Комментарии своего ролика](https://business-api.tiktok.com/portal/docs/get-comments-on-an-owned-video/v1.3) · [Ответы ветки](https://business-api.tiktok.com/portal/docs/get-all-replies-to-a-comment/v1.3)
2. **Изменения после подключения.** Если у цеха появится доступный TikTok HTTPS-адрес, можно принимать `comment.update` о создании, удалении и изменении видимости реплик, сохранять уведомления и учитывать их при запуске по кнопке. Первичной загрузкой закрывается период до подписки. После пропуска доставки нужна сверка доступных данных. Для локального цеха без внешнего обработчика остаётся получение страниц по запросу. [Событие комментария](https://business-api.tiktok.com/portal/docs/comment-update-event/v1.3) · [Проверка подписки](https://business-api.tiktok.com/portal/docs/get-tiktok-account-webhook-configurations/v1.3)
3. **Проверка пригодности до замены текущего коннектора.** После одобрения приложения попросить владельца предоставить права чтения роликов и комментариев. На одном своём ролике подтвердить чтение списка, нескольких страниц одной большой ветки и нового ответа под старым комментарием. Если планируются уведомления, проверить доставку и повтор события. Возможности хранить исходные тексты, сроки хранения и условия доступа для нашего сценария нужно подтвердить при рассмотрении заявки. Стоимость и скорость работы на аккаунте пока не проверены. [Accounts API](https://business-api.tiktok.com/portal/docs/accounts-api-overview/v1.3) · [Официальный SDK TikTok](https://github.com/tiktok/tiktok-business-api-sdk)

## Что произошло в цехе

18 ноября 2026 запуск `6e9def7a-be3e-4b5d-984e-8da500ec2ced` обработал 20 роликов. Из 2 082 прочитанных реплик в выбранный период попали 348. Цех сохранил 6 идей. Из 2 ч 33 мин 30 с примерно 2 ч 20 мин заняли интервалы между повторными попытками. Это реконструкция по таймерам и отметкам запуска. Секундомер отдельно для сетевого чтения в этой версии отсутствует.

| Где возникла проблема | Что показала проверка |
|---|---|
| Одиночная ошибка страницы влияет на весь источник | Сборщик берёт максимум из числа общих неудач и числа неудач конкретной страницы. После успешных запросов к другим роликам старая ошибка снова увеличила общую паузу. |
| Сбор углубляется в ветки каждого ролика до перехода к следующему | Из 399 запросов 334 ушли на ответы в 252 ветках, 48 на основные комментарии, 3 на профиль и список роликов. Ещё 14 попыток вернулись с временным отказом. |
| Состояние работы привязано к одному запуску | Локальная база сохраняет записи и идеи. Курсоры и отложенные страницы переживают перезапуск сервера внутри активного сбора, но при его завершении удаляются. В результате нельзя адресно продолжить 22 незакрытые ветки предыдущего запуска. |
| Лимит чтения и период отбора действуют в разном порядке | Читатель расходует лимит в 191 реплику на ролик до фильтра по дате. На семи роликах он исчерпался. Поэтому из отчёта нельзя заключить, что найдена каждая реплика за 30 дней. |
| Один статус описывает и выполнение, и полноту | Очередь обработала 20 из 20 роликов, подборка сохранена. В 22 ветках на 10 роликах полнота осталась неизвестной. Общая надпись «Частичный результат» скрывает это различие. |

Проверка на данных запуска выполнена локально, в режиме чтения. Штатный отбор получил одинаковые 20 публикаций в обоих вариантах. Со 120 основными комментариями он воспроизвёл пять итоговых тем. Со всеми 348 репликами, включая 228 ответов, он воспроизвёл все шесть по идентификаторам. Ответы добавили тему «AI-инженерия и дата-инженерия — что выбрать» и дополнительные основания. Это проверка результата на уже полученной выборке. Она не измеряет скорость другого сетевого обхода.

В 122 из 252 отдельно запрошенных веток все ответы помещались в диапазон от одного до трёх. Сверены уникальные ID и заявленное число ответов. Для этих веток имеет смысл проверить получение ответов вместе с родительским комментарием через официальный интерфейс. Фактическое число сэкономленных запросов нужно измерять при наличии доступа. 132 свежих комментария пришли под 11 роликами старше выбранных 30 дней, поэтому дату ролика нельзя использовать для исключения его обсуждений.

## Как должен работать запуск по кнопке

1. **Зафиксировать выборку.** При старте сохранить список выбранных роликов, окно дат и действующие лимиты. Сохранить отдельно, сколько уникальных реплик просмотрено и сколько попало в окно. Текущий лимит в 191 прочитанную реплику сохраняет своё значение для существующих настроек. Если нужен лимит именно на реплики за период, это отдельное изменение смысла настройки.
2. **Сначала охватить ролики.** По очереди читать страницы основных комментариев разных роликов, сохранять доступные вложенные ответы и сразу обновлять идеи. Непрочитанные страницы и ветки помещать в ту же долговечную очередь. Распределять работу между основными комментариями и ответами, чтобы при конечном лимите одна длинная ветка или большое число основных комментариев не вытеснили весь остальной материал. Правило распределения и порядок должны воспроизводиться после перезапуска. Изменение порядка при конечном лимите может изменить выборку.
3. **Хранить положение по каждой ветке.** В существующей SQLite держать профиль, ролик, родительский комментарий, положение в выдаче, последнюю проверку, причину остановки и следующую разрешённую попытку. Записывать результаты страницы и новую позицию в одной транзакции. Повторная доставка одной страницы обновляет записи по ID. Следующая кнопка запуска переиспользует сохранённое и проверяет новые реплики и незакрытые ветки. Обход имеет конечную границу по настройкам. Неполные ветки с причиной и позицией остаются доступны для дозабора. Истёкший курсор требует повторной сверки с перекрытием и удалением дублей. Одинаковый счётчик комментариев не доказывает, что состав обсуждения остался прежним.
4. **Развести ожидание ветки и источника.** Недоступная ветка получает своё время следующей проверки. Остальные готовые задачи продолжаются. Явное ограничение источника и указанное площадкой время ожидания действуют на весь источник. При одинаковых временных отказах у разных роликов делать одну контрольную попытку после общей паузы. Успешная выдача снимает общую паузу, история отказов отдельной страницы остаётся только у этой страницы. Запрос повторной авторизации или прямой отказ в доступе нужно отразить отдельной причиной.
5. **Считать идеи и аналитику независимо.** Идеи обновляются по мере поступления подтверждённых оснований. Снимки аналитики живут отдельно от лимита роликов для идей. Для своего профиля при доступном официальном канале события комментариев могут пополнять очередь между ручными запусками. Обработка идей по-прежнему начинается по кнопке. Если нет постоянно доступного обработчика событий, используется сверка по кнопке. После уведомления об удалении или изменении видимости нужно обновить доступность основания в библиотеке и экспортируемых материалах. Пробелы в период недоступности проверяются повторно.
6. **Показывать, что именно готово.** На этом запуске панель могла бы показывать «Обработано 20 из 20», «Сохранено 348 комментариев и 6 идей» и «У 22 веток остались неподтверждённые ответы». Указанный лимит и отказ площадки получают разные причины. В отчёте хранить фактическое время ожидания, время остальной работы и число запросов по типу задачи.

## Порядок внедрения и проверка

Сначала подтвердить для своего профиля возможность доступа к официальному чтению роликов, комментариев и ответов с нужными разрешениями и согласованным назначением приложения. Одновременно можно переработать очередь и учёт покрытия в SQLite на записанных ответах. Текущий публичный коннектор при этом остаётся доступным источником с явно указанными ограничениями. Для этой задачи достаточно одного серверного процесса и существующей базы.

Приёмка на сохранённых данных включает следующие проверки:

- Полный повторный анализ тех же 348 записей воспроизводит все шесть ID идей. Доставка одной страницы дважды и перезапуск между получением и записью не создают дублей.
- Ошибка одной ветки оставляет другие ролики доступными. Общая пауза соблюдает срок площадки. Перезапуск сохраняет позицию и срок, повторная кнопка не создаёт вторую параллельную очередь для того же источника.
- Поздний ответ на старый ролик и новую реплику в давно известной ветке можно найти при следующей сверке. Обработка пропуска в событиях и истёкшего курсора сохраняет установленные пределы и отмечает непроверенный диапазон.
- После обхода 20 роликов отчёт показывает охват, ограничение по настройкам и конкретные незакрытые ветки. Дозабор использует их идентификаторы. Сравнение скорости имеет смысл только при сопоставимых настройках и покрытии, с независимым учётом пауз и потерянных оснований.

## От выборки до материалов

Один запуск сохраняет настройки источников и привязывает полученные публикации и комментарии к своему номеру. Для TikTok окно чтения длится до пяти минут и заканчивается раньше при паузе площадки. Следующее нажатие использует сохранённые позиции чтения. Пустые реплики и уже обработанные тексты не заполняют выборку идей. После окончания общей паузы цех сначала читает остальные недочитанные ролики, затем возвращается к отложенным, начиная с самого давно отложенного.

После сбора задание обработки сохраняется в SQLite в `result_jobs`. При перезапуске сервера обработка продолжается с последнего сохранённого этапа. Статистика в полном цикле обновляется отдельно и учитывает паузу площадки. Запуск одной площадки доводит материалы до отчёта ядра и пропускает аналитику.

Перед отправкой выборки цех резервирует комментарии в `ai_input_claims`. Для фонового запроса OpenAI он сохраняет номер принятого задания, затем читает результат по этому номеру. Ответ записывается до проверки оснований. Отчёт, учёт использованных комментариев и снятие резерва фиксируются одной транзакцией. Повторное открытие материалов читает сохранённые отчёты. При обрыве во время отправки до получения номера задания возможное списание неизвестно, и автоматический повтор блокируется. [Фоновые задания OpenAI](https://developers.openai.com/api/docs/guides/background)

Библиотека объединяет темы по подтверждённым связям, сохраняет оригинальные ссылки в основаниях и учитывает отклонённые связи. Вкладки браузера согласуют импорт через одну блокировку. Пользовательские удаления учитываются при импорте.
